# 第五阶段：公开推广与成本控制

> 承接《第四阶段-用户自带密钥设计》。这一阶段要回答的不是"怎么加密密钥"，
> 而是 **"这个系统要不要向陌生访客要密钥"**——一个产品判断，附带一套成本护栏。

## 1. 问题：两个受众被塞进了一个入口

第四阶段做完 BYOK 后，页面上只有一个入口——「创建 / 切换身份」，
里面既有身份切换，也有「大模型 Key」表单。这在自用时毫无问题，对外推广时立刻分裂：

| 受众 | 他们想要的 | 打开页面看到的 |
| --- | --- | --- |
| **面试官 / 同学 / 老师**（路过看看） | 点开就问，30 秒内判断这东西值不值得看 | 一个要他先交出 API Key 的表单 |
| **想自己部署的人**（真用户） | 用我自己的模型和额度 | 正好想要的表单，但混在"身份"里 |

于是同一个界面，对第一类人是**劝退**，对第二类人是**找得到但别扭**。

更麻烦的是信任：即使我们把密钥 Fernet 加密、只回掩码、禁止内网地址，
这些全是**代码里的善意，用户看不到**。在陌生人眼里，"小站点要求粘贴 API Key"
和钓鱼页的视觉特征完全一致——这不是技术问题能解决的。

## 2. 结论：拆形态，不删能力

**能力保留，入口分形态。** 一个环境变量（`SCHOOL_DEPLOY_MODE`）决定"要不要采集密钥"：

| 形态 | 默认 | 模型设置入口 | 默认回答方式 | 费用承担 |
| --- | --- | --- | --- | --- |
| `public` | ✅ | **不渲染**，写接口 403 | 原文摘编（零成本） | 部署方，受每日额度约束 |
| `selfhost` | | 渲染（BYOK） | 大模型生成 | 用户自己 |

默认 `public` 是刻意的取舍：**宁可让自部署者多写一行配置，也不要让对外站点默认向陌生人要密钥。**
反过来（默认 selfhost）一旦部署者忘记改，代价是"在公网上向陌生人要密钥 + 每次提问都花自己的钱"，
这是更糟的失败方向。

代码层面 `byok_allowed` 只有一个来源，避免两处开关打架：

```python
@property
def byok_allowed(self) -> bool:
    return self.deploy_mode == "selfhost"
```

## 3. 三道闸门：公开形态下"要不要花钱"

判定顺序在**路由层**（`plan_answer`），不在检索编排里——"该不该花钱"是部署策略，
混进 `QAService` 会让检索逻辑无法单独测试。

```
mode = resolve(requested_mode)        # auto → 按部署形态推导
① mode != llm            → 摘编，不调模型
② 没有可用密钥            → 摘编 + 提示
③ public 且额度用尽       → 摘编 + 提示原因
否则                     → 生成
```

三条"拒绝"都不是错误：摘编返回的是**完整答案 + 引用**，只是没有经过模型归纳。
所以用户侧看到的是「答案朴素」而非「报错」，HTTP 仍是 200。

实现上还有一个细节：摘编模式下不是"加一个 if 跳过生成"，而是**换掉 LLM 客户端**
（`deps.disabled_llm`）。这样多轮指代改写也会自动走零成本启发式，不需要在每个调用点判断开关。

## 4. 额度：为什么是 fail-closed

`app/service/llm_quota.py`，表 `llm_usage(day, scope, subject, count)`：

| 维度 | subject | 默认上限 | 防的是 |
| --- | --- | --- | --- |
| `user` | 随机 `user_id` | 30 次/天 | 单个刷子 |
| `global` | `'all'` | 300 次/天 | 众生踩踏 |

四个设计决定：

1. **按天分区**：`day` 是本地日期字符串，跨天自然归零，不需要定时清理任务。
2. **只记次数**：不存问题内容、不存 IP，`subject` 是随机 user_id，不关联学号姓名。
3. **fail-closed**：任何异常（锁、磁盘、表缺失）都按"超额"处理 → 退回摘编。
   反过来 fail-open 会让统计失效时账单失控；而退回摘编对用户仍是可用结果。
   这个方向的错误成本最低。
4. **best-effort 计数**：读-判-写在一个事务内完成。单进程精确；多进程并发时
   可能瞬时多放行一两次。额度是**成本护栏**而不是**计费依据**，不值得为它引入分布式锁。

## 5. 成本模型：钱到底花在哪

检索链路（jieba 分词、BGE 向量、RRF 融合、reranker 重排）**全部本地，零 API 成本**。
只有最后一步生成要钱，单次上下文约 2–4k tokens（5 条证据 + 问题），
量级在**分/次**。按默认 300 次/天的全站上限算，最坏情况的日成本是"几元"级别。

因此公开推广真正的门槛不是"钱多"，而是**"会不会被刷"**——这正是额度要解决的问题。
如果连这几元也不想花，把 `ALLOW_SERVER_LLM_FALLBACK=false`，站点就是纯检索问答：
零成本、零密钥风险，且不会被模型改写条款措辞（对制度问答而言反而更可信）。

## 6. 前端职责拆分

| 组件 | 职责 | 出现条件 |
| --- | --- | --- |
| `#identity-box` | 创建身份 / 粘贴 Token 切换 / 退出 | 始终 |
| `#settings-box` | 模型设置（Base URL / 模型 / Key），保存 / 测试 / 清除 | 仅 `byok_allowed` |
| `.mode-row` | 回答方式切换（原文摘编 / 大模型增强） | 仅 `effective`（确有可用模型） |

三条原则：

- **不给做不到的选项**：没有可用模型时，切换器直接不显示，而不是显示后点了无效。
- **拿不到策略就按最保守处理**：`GET /llm/config` 失败 → 当作 public，藏起密钥入口。
- **"改用大模型"不自动重发**：点击只把原问题填回输入框并切模式，由用户自己发送。
  自动重发会把同一条问题再写一遍会话历史，造成"一条问题两条回答"的脏数据；
  宁可多按一次回车。

## 7. 刻意不做的三件事

| 不做 | 原因 |
| --- | --- |
| 语义缓存高频问题 | 见效最明显但也最容易出错：缓存命中要保证引用与版本一致，否则会把旧通知当新答案返回。留到有真实流量数据后再做 |
| 纯前端直连（key 只存浏览器） | 看似"不需要信任服务端"，但失去服务端日志与额度，且部分厂商不支持浏览器跨域；降级体验更差 |
| 引入 Redis/PG 做计数 | 为 300 次/天的规模引入新组件，运维成本远大于收益 |

## 8. 验证

`tests/test_deploy_mode.py`（16 项）覆盖：

- 两种形态的默认回答方式、`byok_allowed`、写接口 403（`detail=byok_disabled`）
- 三道闸门：摘编默认 / 无密钥提示 / 单用户超额 / 全站超额
- 额度：按天独立、双维度关闭即不限、**存储异常时 fail-closed**
- 服务层：摘编答案仍带引用且 `can_enhance=True`；FAQ 命中即便请求生成也不花钱
- `GET /health` 暴露形态字段；非法 `mode` 返回 400

双形态冒烟（临时实例，不碰 8000）：

```bash
# public
SCHOOL_DEPLOY_MODE=public python -m app.cli serve --port 8010
# selfhost
SCHOOL_DEPLOY_MODE=selfhost python -m app.cli serve --port 8011
```

## 9. 回滚

形态是纯配置：把 `SCHOOL_DEPLOY_MODE` 改回 `selfhost` 即恢复第四阶段行为，
无需改代码、无数据迁移。`llm_usage` 表只增不改，回滚后可保留（不参与业务读取路径）。
