# 第六阶段：身份分档与模型接入

> 对应代码：`app/service/users.py`、`app/service/llm_config.py`（系统默认模型部分）、
> `app/web/deps.py`（`request_llm_config`）、`frontend/js/{user,chat,admin}.js`
> 前置阅读：[第四阶段-用户自带密钥设计.md](第四阶段-用户自带密钥设计.md)、[第五阶段-公开推广与成本控制.md](第五阶段-公开推广与成本控制.md)

## 1. 这一版解决什么

两个边界问题，都不是「功能缺失」，而是**职责放错了位置**。

**问题一：身份面板在管模型。** 上一版把「⚙ 模型设置」放在侧栏身份卡旁边，结果是：任何人点开
「切换身份」都会先看到「请粘贴你的 API Key」。身份回答的是「我是谁」，模型回答的是「用哪个引擎」；
前者跟着人走，后者跟着会话走，混在一起会让第一次访问的人以为这个站点要他交密钥。

**问题二：老师身份可以自己建。** 原来的创建接口只校验「系统里有没有用户」，
不看角色，于是任何匿名访客都能创建一个 `role=teacher` 的账号，从而获得增量入库与评测权限。
在校内场景里，这个角色本该由学校背书，不能自封。

## 2. 身份策略

### 2.1 三条规则，按优先级

| 场景 | 允许创建的角色 | 理由 |
|---|---|---|
| 系统内没有任何用户（bootstrap） | 任意 | 否则永远产生不了第一个管理员，空库死锁 |
| 调用方是 admin | 任意 | 名单注入走这条路 |
| 其他人（匿名 / 学生 / 老师） | 仅 `student` | 老师与管理员不开放自助，避免自封身份 |

实现位置：`app/service/users.py::create_user`。前端同步去掉角色下拉，只保留「创建学生身份」。

### 2.2 名单注入

`POST /api/v1/users/bulk`（仅 admin）：

```json
{
  "users": [
    {"username": "zhangsan", "role": "student"},
    {"username": "lisi", "role": "teacher"}
  ],
  "dry_run": false
}
```

返回三分明细，**逐条处理而不是整批事务**——一份上百人的名单里有一行格式错误，
不应该让其余 99 个人都进不来：

```json
{
  "dry_run": false,
  "total": 4,
  "created": [{"line": 1, "username": "zhangsan", "role": "student", "api_token": "…"}],
  "skipped": [{"line": 3, "username": "zhangsan", "reason": "本次名单内重复"}],
  "failed":  [{"line": 4, "username": "bad1", "reason": "角色必须为 admin/student/teacher"}],
  "summary": {"created": 2, "skipped": 1, "failed": 1}
}
```

三条设计约束：

1. **幂等**：已存在的用户名落入 `skipped`，重复提交不会产生重复账号；
2. **dry_run**：只校验与去重、不写库，用于导入前预览（前端「预览」按钮）；
3. **token 只出现一次**：`created` 里带 `api_token`，之后任何接口都不再回显，界面提示当场分发。

前端三种输入方式共用同一套解析（`用户名,角色`，角色可省略、支持中文别名），
文件导入只是把文件内容读进文本框，不引入第二套规则。

## 3. 模型接入

### 3.1 三种来源与优先级

`app/web/deps.py::get_llm_for_user`：

| 顺序 | 来源 | 存储位置 | 生效范围 |
|---|---|---|---|
| 1 | 请求头 `X-LLM-*` | 浏览器 localStorage | 单次请求 |
| 2 | 用户 BYOK 配置 | `user_llm_configs`（Fernet 密文） | 该用户 |
| 3 | 管理员默认模型 | `system_llm_config`（单行，密文） | 全站 |
| 4 | `.env` | 部署文件 | 全站 |
| 5 | 都没有 | — | 降级为原文摘编 |

### 3.2 为什么自定义密钥放在浏览器

用户对「小团队会不会盗用我的额度」的怀疑，靠代码注释无法消除。把密钥留在浏览器有两个直接好处：

- **可验证**：用户打开开发者工具就能看到它在哪、能一键删掉，不需要相信任何承诺；
- **实现更简单**：不需要为用户密钥维护一张加密表、一套主密钥轮换与清理级联。

但「存在浏览器」不等于「前端直连模型」——绝大多数模型服务不允许浏览器跨域调用（CORS），
所以链路是：前端取出密钥 → 随请求头发给后端 → 后端仅用于本次调用 → 返回结果。
服务端**不落库、不写日志、不进入任何响应**。

因此这套方案的安全性由三件事共同保证，缺一不可：

1. 服务端不持久化（代码约束）；
2. 日志脱敏（`log_event` 不记录请求头）；
3. 传输加密——**线上必须 HTTPS**，本地开发限 `127.0.0.1`。

### 3.3 管理员默认模型

`system_llm_config` 是单行表（`id = 1`），只存 `base_url / model / api_key_enc / key_hint / updated_by`。

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /api/v1/llm/default` | admin | 只回掩码；`source` 标明来自 `db` / `env` / `none` |
| `PUT /api/v1/llm/default` | admin | `api_key` 留空 = 沿用已存的那把（只改模型名） |
| `DELETE /api/v1/llm/default` | admin | 删除后退回 `.env`，不是把系统变成不可用 |

之所以落库而不是只读 `.env`：换默认模型是运营动作，不该要求改文件 + 重启。
改完下一次请求即生效（不做缓存，避免「改了还在用旧的」）。

### 3.4 前端交互

- **模型选择器**：输入框下方常驻，显示当前模型名；点开可选择「服务端默认」或已保存的自定义模型，
  也可新增（Base URL / 模型名 / API Key + 「测试」）。
- **按身份隔离**：`localStorage` 的键是 `llm_models_<user_id>` 与 `llm_active_<user_id>`，
  换身份后自动换成对方那份，避免学生误用老师配置的额度。
- **匿名访客**：能看到服务端默认模型，但「添加自定义模型」不显示——没有身份就没有保存配置的位置。
- **选中自定义模型后自动切到「大模型增强」**：选了模型却仍走原文摘编没有意义，用户可再手动切回。

## 4. 降级与错误矩阵

| 情况 | 表现 | 是否 5xx |
|---|---|---|
| 请求头 base_url 非法（非 http/https、内网地址） | 400 `INVALID_INPUT`，提示具体原因 | 否 |
| 自定义模型不可达 / 鉴权失败 | 降级为原文摘编 + `degraded=true`，答案仍完整 | 否 |
| 匿名用户尝试保存自定义模型 | 前端不显示入口；服务端接口按身份拒绝 | 否 |
| 非 admin 调 `/llm/default` | 403 `FORBIDDEN` | 否 |
| `public` 形态带 `X-LLM-*` 请求头 | 完全忽略（不采集密钥的承诺不能有例外） | 否 |
| 日志字段与 LogRecord 属性重名 | `log_event` 自动加前缀，不影响请求 | 否 |

## 5. 已知边界

1. `public` 形态下不开放任何自定义模型入口，即使后端接口存在——这是产品决策，不是能力缺失。
2. 自定义模型配置不跨设备同步：换浏览器或清缓存后需要重填。现阶段可接受。
3. 没有「删除用户」接口，`user_llm_configs` 暂未做级联清理（与第四阶段遗留一致）。
4. 名单导入逐条创建，上百人名单会逐条哈希与写库；当前规模（校内几百人）足够，
   更大规模应改成单事务批量插入。
